# Sister project: TagApp 6.0

Scope: how TagAppVault and TagApp 6.0 relate, what they share by copy, where they differ on purpose, and how to port a feature from one to the other. The mirror of this doc is `docs/sister-project.md` in the other repo.

- **This repo (TagAppVault)**: self-hosted media library. Downloads (server or CLI) land in a library on disk; a React web UI browses and tags it ([README](../README.md)).
- **Sister (TagApp 6.0)**: `/home/dil/CRS/Projects/NewProjects/TagApp/TagApp6.0`. Chrome MV3 clipper extension (WXT) that saves and tags content from websites, with an optional server of its own (Hono + oRPC + LowDB) and a small read-only web UI. Its own docs: `TagApp6.0/AGENTS.md`.

They are separate repos with no shared package: everything shared is **copied**. Neither imports the other.

## Runtime connection

The extension is the producer, the Vault the consumer. There are four touch points; the Vault never calls the extension.

1. **Queue push.** In the extension's library the "Send N to server" button (`apps/extension/src/components/craft/ServerAffix.tsx`, URL set in Settings > Connected pages) POSTs `{ items: ContentWebType[], groups: GroupType[] }` to the Vault's `POST /downloads/set` (`apps/server/src/index.ts`, body `downloadsSetSchema`, handler `setDownloads` in `packages/api/src/services/downloads.ts`). Shapes: [domain model](./domain-model.md#schemas); `groups` = `referencedGroups(items, groups)`, the records of every group id on the sent items. The items are the filtered library rows plus the children of shown group cards, deduped (`entryItems`), sent as stored (no constants applied) except that the extension drops its `local:*` tags from items and groups first. No bare array.
2. **Host-page tag broadcast.** The Vault page origin is in the extension's `hostNames`; its content script posts `TAG_APP_INJECT_TAGS` (`payload: string[]`, the extension's tag list, plus `covers: Record<tag, url>`: only tags with a cover, `$Key` constants already expanded, because the Vault cannot expand them; the Vault validates it and shows the covers on `/tags`, an extension without `covers` still works) and the Vault replies `TAG_APP_TAGS_RECEIVED` and appends `RESERVED_TAGS` ([web app](./web-app.md#extension-handshake-and-read-only-mode)). Until then the Vault UI is read-only. Extension side: `TagApp6.0/docs/clip-flow.md`.
3. **Ids.** Item ids and group ids chosen in the extension become Vault ids (items are named `<title>.<id>` on disk, [domain model](./domain-model.md#identity)). Group ids have the same shape on both sides (`grp_<nanoid10>`, `newGroupId` here); `groups.changeId` re-keys a Vault group (an existing target merges) to line a stub or an older group up with the extension's id.
4. **Sync with server.** The extension's "Sync N with server" button (`ServerAffix.tsx`, its own URL `syncServerUrl`, Settings > Connected pages) POSTs `{ items: { id, title, tags, extraData }[] }` (a subset of `ContentWebType`, the same filtered items minus the extension's `local:*` tags, no groups) to `POST /content/sync` (`apps/server/src/index.ts`, body `contentSyncSchema`, handler `overwriteContent` in `packages/api/src/services/overwriteContent.ts`). Answer `{ updated, missing, failed }`. Rules: [file operations](./file-operations.md#overwritecontent-post-contentsync).

Conflict rules (all on the Vault side, [groups](./groups.md#downloads-and-sync)):

- **The Vault wins for groups.** `registerGroups` adds only ids it does not know (tags counted); known records are never overwritten and the incoming `cover` is dropped (the Vault sets covers itself, set once from the first synced child).
- **Items**: the queue de-duplicates by id (first wins); an id already in the library is dropped without downloading; a run in progress keeps its running items ([server downloads](./server-downloads.md)). Items keep their `groups` ids through the staging sidecar into the library; sync creates a stub (`title = id`) for any group id still unknown.
- **Local tags**: the extension strips its `local:*` tags (parent `local`, or the bare tag `local`) from items and groups before posting, so none arrives here. The `TAG_APP_INJECT_TAGS` broadcast leaves them out too.
- **Sync with server: the extension wins** for title, tags and extraData of items already in the library (the opposite of groups); ids it does not know are skipped, never created. Group records are not sent, so group edits still do not travel either way.
- **No reverse sync.** Edits made in the Vault (group titles, tags, merges) never travel back to the extension, and re-posting to `/downloads/set` does not update them; only `/content/sync` overwrites existing items.

## Differences that stay on purpose

- The Vault has **no local/remote mode**: one server, one UI. 6.0 duplicates every behaviour as local (extension atoms) and remote (its server), and its UI goes through adapters (`useGroupOps`).
- Vault only: disk layout, sync, download queue and runner, CLI, Caddy, `meta:*`/`view:*` tags, galleries/video/audio/text pages, `/sync`, `/downloads`, `main.setContent` file moves. 6.0 only: clip flow, site scripts, profiles, backup and restore, after-add/remove scripts, the extension popup.
- The Vault's web app edits; 6.0's own `apps/web` is read-only and has no `/group` list.
- Covers: the Vault stores plain URLs (`/media/...`); 6.0 stores `$Key` constants and expands them (`useGroupCover`). Fix Data differs accordingly ([groups](./groups.md#cover)). The Vault has no backup/restore.
- `ModalShell`: stock `Dialog` here; hand-rolled in 6.0 (it must work in the content script's shadow root). Delete texts say "from the server" only here. `TagApp6.0/docs/groups.md` ("UI parity with the Vault") lists the rest.
- "Grouped items in the library" (Settings): here localStorage `grouped_in_library` and a Select, a field of `FilterQueryAtom`. 6.0 stores it globally in WXT storage (`local:groupedInLibrary`, readable by the clip overlay), shows the same labels and help text as a button group (like its group position), and adds it to the query when the filter runs. 6.0's read-only `apps/web` has no settings page and keeps `hide`.
- Commands: here `bun type:check` works and `bun test packages/api|utils|cli` exist; in 6.0 root `type:check` is broken (`bunx tsc --noEmit` in `apps/extension`, `bunx tsc -b` in `apps/web`) and `bun test` covers `packages/utils` only. Both: `bun check`.

## Porting a feature between the projects

Addressed to coding agents. When the user asks for something "like in TagApp 6.0" (or the reverse), port it; do not reinterpret it.

1. **Read the source side first**: its code and its doc (`TagApp6.0/docs/*.md`, e.g. `groups.md`), and `git log` there for the commits that introduced it. Existing parity commits ("groups UI parity with ...") show the expected scope.
2. **The UI stays in parity**: same labels and wording, layout and order, icons, button variants, tooltips and aria-labels, empty/loading/error states, toasts, confirm dialogs and their texts, behaviour, and where a setting lives. Do not restyle or "improve" while porting; if something cannot match, keep it in "Differences that stay" above and in the feature's doc.
3. **Shared logic goes to the matching file** (table above), keeping the same names and behaviour. Adapt only what differs by design: no mode branching and no `$Key` constants here; tag deltas instead of in-state counts; disk and sync concerns in `packages/api`. If a shared schema changes, check the `POST /downloads/set` contract in both repos.
4. **Use this repo's conventions**: components in `components/craft` (never edit `components/ui`), router files export procedures only, file operations roll back, counts stay in sync ([AGENTS.md](../AGENTS.md)).
5. **Update both repos' docs** in the same change as the code: the feature's doc (usually `groups.md`) on both sides, `mock-pages.md` and the mock data when pages or states change, and this doc when the table or a difference changes. If you are only asked to change one repo, say in your reply what the other repo still needs.
6. **Run this repo's checks** (and the other's if you edited it): `bun check:fix`, `bun type:check`, `bun test packages/api` / `packages/utils` where touched; 6.0: `bun check:fix`, `bunx tsc --noEmit` in `apps/extension`, `bunx tsc -b` in `apps/web`, `bun test packages/utils`. Check UI changes on the mock pages ([mock pages](./mock-pages.md)).
7. Commit per repo (the repos are separate; no cross-repo commit), several small commits with the docs in the same commit as the code ([development](./development.md#git)); 6.0 uses conventional messages (`feat(web): ...`).

Checklist: source read, UI identical (labels, icons, toasts, confirms, states), shared files ported, differences documented, mock pages updated, both docs updated, checks run per repo.
